# Dependency Injection

How the server's services move from static classes to instances built by a dependency-injection container, and how to convert one. The decisions are in `MaintainabilityRefactorSpecs.md` (Phase 2); this guide is the working recipe, with the pilot (`Achievement`, `Faction`, `Taxi`) as the example. Read it before converting a service.

Sections: The pattern · The container · Converting a service · A service of several classes · Dependencies · Tests · Rules the architecture tests enforce · Pitfalls

## The pattern

A converted service is three pieces. Callers, content definitions and event handlers keep using the static class, so nothing outside the service changes.

| Piece | Where | What it is |
|---|---|---|
| Facade | `Service/<Name>.cs`, namespace `SWLOR.Game.Server.Service` | The static class every caller already uses. Same public members, same signatures. Each member forwards to the instance. It keeps the `[NWNEventHandler]` methods and the `const` fields. |
| Interface | `Domain/<Domain>/I<Name>Service.cs` | One member per public member of the old static class, with the doc comments. |
| Instance class | `Domain/<Domain>/<Name>Service.cs` | The old logic moved verbatim. Static state becomes instance fields. Dependencies come through the constructor. |

`<Domain>` is the domain the service is in `SWLOR.Architecture.Tests/DomainMap.json` (Core, UI, Combat, Abilities, Character, Items, Crafting, Economy, Quests, World, Space, Creatures, Companions, Social, Administration, Gameplay). The namespace is `SWLOR.Game.Server.Domain.<Domain>`, never `SWLOR.Game.Server.<Domain>`: a namespace named like a service (`Combat`, `Space`) or like an existing folder (`Core`) would capture simple names such as `Combat.CalculateHitRate()` in every file below `SWLOR.Game.Server`. Inside `Domain.*` code, a name that is also a domain (`Combat`, `Space`) still means the facade only when spelled `Service.Combat`.

The support types of the service (the enum, the attribute, records) stay where they are, in `Service/<Name>Service/`. Moving them would change the `using` of every caller; they move when the facades are removed (Phase 2, P2-Z).

The facade, as converted (`Service/Achievement.cs`):

```csharp
public static class Achievement
{
    private static IAchievementService Instance => FacadeAccessor.Resolve<IAchievementService>();

    [NWNEventHandler(ScriptName.OnModuleLoad)]
    public static void ReserveGuiIds()
    {
        Instance.ReserveGuiIds();
    }

    public static void GiveAchievement(uint player, AchievementType achievementType)
    {
        Instance.GiveAchievement(player, achievementType);
    }
    // ... one forwarding member per member of the interface
}
```

A `const` cannot forward, so the facade repeats it from the instance class: `public const int MinimumFaction = Domain.Quests.FactionService.MinimumFaction;` (spell the namespace: `FactionService` alone means the namespace `Service.FactionService` inside `namespace SWLOR.Game.Server.Service`). Compile-time constants are inlined, so callers (the toolset included) are unaffected.

## The container

Code lives in `Composition/`.

- `ContainerHost` builds a container once, with `ValidateOnBuild` and `ValidateScopes`, and creates every singleton during the build. A missing dependency, a lifetime mistake or a constructor that throws stops the boot, not the first handler that needs the service. A second build, or asking before the build, throws `ContainerNotBuiltException`.
- `CompositionRoot.ServerHost` is the server's container. `ServiceRegistrations` lists the services, one line each, grouped by domain. Every game service is a singleton (process lifetime; there are no scoped services in this phase).
- `FacadeAccessor.Resolve<T>()` is the one internal accessor facades use. Nothing else may resolve from the container (see the rules below).
- `ServerBootstrapper` runs a named step list (`Steps`). `BuildServiceContainer` comes after the internal systems (logging, the script execution provider) and before `RegisterEventHandlers`, `LoadEngineTestAssembly` and `LoadScripts`. Handlers exist only after `LoadScripts` registers them, and the engine cannot call back into the server before `Bootstrap` returns, so the container exists before any handler, `mod_preload` included. `LoadScripts` refuses to run without the container, and `ServerBootstrapperOrderTests` pins the order.
- A constructor must not call the engine or read other services' state: singletons are created while the server boots, before the module loads. Do engine-dependent setup in a handler (the facade forwards it), as the services always did.

`FacadeAccessor.Resolve<T>()` reads a per-service cache (`Composition/FacadeCache<T>`) instead of asking the container on every call: one static slot per service type holds the instance and the container it came from. A call compares that container with `CompositionRoot.Current` (reference check) and returns the instance, with no dictionary lookup and no allocation. The slot is valid only for its own container, so nothing needs clearing: when the container is built, replaced or rebuilt (Phase 4 hot reload), or a test installs its own, `Current` names another container, the check fails and the next call resolves and refills the slot. A cached instance is therefore never served for a container that is no longer current, and fixtures that install different `FacadeContainer`s are safe, also when they run in parallel (they refill the slot, which costs one lookup). Two threads that miss together both resolve and both write; services are singletons, so both get the same instance and the race is benign. Before the container exists `Current` throws `ContainerNotBuiltException` as before. Measured with `Bank.IsFull` in Release (`FacadeCacheTests.Measure_facade_call_cost`, an explicit test): about 8-9 ns per facade call against about 4 ns for a direct instance call, down from about 26 ns before the cache.

Tests that need their own container build one with `ContainerHost.Create(services)` and make the facades use it for the current async flow with `CompositionRoot.InstallForTests(provider)`. Production code never calls it (`CompositionSourceGuardTests` fails if it does).

## Converting a service

One service per pull request. Each pull request also brings the service's own lines to at least 70% coverage.

1. Read the service, its folder, its callers (the service's edges in `SWLOR.Architecture.Tests/Baseline/CrossDomainEdges.txt`), its handlers (`Core/ScriptHandlerOrder.txt`) and its tests. Look for tests that recompile its source with Roslyn or reset its static state by reflection; they are replaced in step 7.
2. Create the interface and the instance class in `Domain/<Domain>/`. Move the logic and state verbatim: statics become instance fields, `static` goes off the methods (private helpers included), nothing else changes. A `const` the logic uses moves with it (the facade repeats a public one); a public `const` the logic does not use (`PlayerMarket.MaxListingsPerMarket`) stays on the facade. A public static property becomes an interface property, and the facade repeats it as a getter-only static property (`public static int MaxRank => Instance.MaxRank;`), which has no backing field. Keep strings that name the service (a GUI id reservation made under `nameof(Achievement)` stays the literal `"Achievement"`; do not reference the facade from the instance).
3. Turn the old file into the facade: keep the class, the handlers and the constants, forward every public member to `Instance`. Keep the doc comments.
4. Register the interface in `Composition/ServiceRegistrations.cs` (one line) and add the service, sorted by name, to `SWLOR.Architecture.Tests/ConvertedServices.json`.
5. Handlers stay on the facade. The instance class has no `[NWNEventHandler]`: the script registry binds handlers as static methods, and the handler order manifest keeps its names (`SWLOR.Game.Server.Service.Achievement.LoadAchievements`). Do not move a facade to another namespace or file path; a move renames its handlers and can reorder reflection (the manifest keeps the run order). A handler that must change its name (it moved onto a facade) is listed in `tools/Refactor/HandlerRenames.txt` as `<master full name> <branch full name>`, in the same pull request, so the parity run and the master sync match it by the branch name.
6. If the old file made player messages, `Readmes/PlayerMessageAudit.json` lists them by file: change `File` (and `Line`) of those entries to the instance file. If `PlayerMessageAuditTests` names the old file in its list of gameplay-outcome files, name the instance file.
7. Write the unit tests (below) and measure coverage.
8. Build and run: the service's tests, `SWLOR.Architecture.Tests`, `SWLOR.Game.Server.CharacterizationTests` (snapshots must not change), the handler order tests (`ScriptHandlerManifestOrderTests`, `ScriptHandlerSeamTests`), and `scripts/ci/run-unit-tests.sh --out <dir>`. For a service with in-game behaviour also run the engine characterization scenarios (`scripts/run-engine-tests.ps1 -Filter Characterization`, `EngineTesting.md`).
9. Record the service, the pull request and the coverage before and after in `MaintainabilityRefactorStatus.md` (the coordinating session does this when it merges).

## Dependencies

| The service uses | In the instance class |
|---|---|
| Another converted service | Constructor-injected interface. |
| A service not converted yet (`Gui`, `Random`, `Messaging`, ...) | The static facade, as before. It converts later and keeps working. |
| `DB` | `IDBService` (`Domain/Core`), implemented by `DBService`, constructor-injected. The static `DB` is its facade (the `OnModulePreload` handler stays there). The Redis connection, entity cache, write versions and index metadata are instance state. Members that only the facade needs (`Load`, `StreamAdd`, `GetRawJson`, `SearchIds`, `SearchRawJson`, `SetUnindexedJsonProperty`, `EscapeTokens`) have a default that throws, so a fake implements only what its test uses (`InMemoryDBService`). A tool that has no game server (`SWLOR.CLI`, `SWLOR.Admin`) builds the container with `CompositionRoot.Build(CompositionRoot.ServerHost)` before `DB.Load()`. Unit tests of the service use `FakeRedis` through the protected virtual seams. |
| The engine (NWScript, NWNX) | Bare calls through the global static imports, as everywhere. Tests swap the engine with `NWScriptRuntime.Override` and the plugin runtimes (`PlayerPluginRuntime.Override`, ...). Do not inject `INWScript`. |
| Native engine objects (`NWNXLib.g_pAppManager`, `CNWSPlayer`, ...) | Not seamed yet. Put each read of native data in a small `protected virtual` method of the instance class whose body is the original code, and let a test subclass answer it. Return a managed value (a record struct, an `int?`) instead of the native object when the rest of the logic needs only a few fields (`ChatPortraitTellsClient`). Keep the native read to the smallest piece that cannot run without a server; the logic around it stays testable. Do not add an interface and a registration for it: `Every_domain_service_in_the_container_is_listed_as_converted` counts every registered `Domain.*` type as a service. The same holds for a call into a service that is not converted yet whose static code reads the database or the native engine for a real player (`Perk.GetPerkLevel`, `StatusEffect.ApplyStatusEffect`): wrap just that call in a `protected virtual` method of the instance class, with the original call as its body (`TrapsService.CanUseTrapTier`, `TrapsService.ApplyBleed`, `MusicService.HasKeyItem`, `WeatherService.GetProtectedDamage`, `FishingService.GiveAgricultureXp`, `LootService.GetPerkLevel`, `LootService.GetStatAdjustment`, `LootService.GetBeastDetail`, `BeastMasteryService.GetPerkLevel`, `BeastMasteryService.ClearCompanionControl`, `ItemService.GetPerkLevel`/`GetPerkName`/`GetCreatureSkillRank`/`GetSkillName` for the perk and skill catalogs, `PropertyService.TogglePlayerWindow` and `CasinoSlotService.TogglePlayerWindow` for `Gui`'s window table, `CapstoneProofService.IsFeatRegistered`/`GetAbilityDetail` for `Ability`'s static ability table, `WardrobeService.ApplyOutfit`/`ApplyHelmet` for the native item writes of `EquippedItemAppearance`), and let a test subclass answer it. The same wrapper fits a call a test cannot wait for or must not make: `PropertyLoaderService.ScheduleLoadBatch` (the load queue's `Scheduler.Schedule`, which runs on the real clock) and `PropertyCityGovernanceService.PropertyBroadcastWebhookUrl` (the webhook the process environment names). Leave the wrapper when the dependency converts. |
| Time, randomness | `Clock` and `Random` as before (`Clock` only in the files the clock seam script owns). A service that compares against `DateTime.UtcNow` and registers `Scheduler` tasks (`ShuttleService`) keeps those calls but puts each behind a one-line `protected virtual` method (`UtcNow()`, `Schedule`, `ScheduleRepeating`) whose body is the original call, so a test can set the time and run the repeating tick and the delayed tasks itself (`ClockedShuttleService` in `Tests/Support/ShuttleBench.cs`). A test of rolls seeds the shared generator (`Random.SetSeed`, `Random.ResetSeed` in `TearDown`) and replays the draws with `System.Random` in the order the service makes them, which also pins their order and number (`FishingServiceTests`). |

Never inject `IServiceProvider` or take the container in a constructor. Dependencies that form a cycle between two converted services cannot be injected both ways: break it by moving the shared part into a third service, or leave one direction on the static facade and say so in the pull request. (`BeastMasteryService` takes `IIncubationFieldNoteService`; `IncubationFieldNoteService` reads the beast catalog through `protected virtual` wrappers over the `BeastMastery` facade.)

## Tests

- **The instance**: `Tests/Domain/<Domain>/<Name>ServiceTests.cs`. Construct the instance with fakes: `InMemoryDBService` for `IDBService` (entities by id, records every `Set`), `PlayerEngine` (a `FakeNWScript` where the target is a player with a UUID; `Messages()` returns what was sent to the player), `FakePlayerPlugin` and the other plugin fakes for NWNX calls. Assert the saved entities, the messages and the engine calls. `InMemoryDBService` cannot evaluate a query: `Search` and `SearchCount` answer with every stored entity of the type and record the query in `Queries`, so store only what the query would match and assert on the recorded query text. Code that runs several searches over one entity type (the contract board's boot sweep) uses `QueryableDBService` (`Tests/Support`), which wraps an `InMemoryDBService` as `Store` and answers a search with the entities whose indexed properties match the query (exact values, lists of numbers and numeric ranges). A call into a service that is not converted yet (`Item`, `Perk`, `Quest`, ...) runs its real static code, so it works only where that code needs nothing but the engine fakes; code that needs the native engine (`Item.FitsInInventory`) or the database (`Perk.GetPerkLevel` on a player) is left to the in-engine tests, and a DM answer from the engine fake stands in for a player with no perks. The pilot and Economy test classes are the examples.
- **The facade**: nothing to write. `FacadeForwardingTests` reads `ConvertedServices.json` and proves for every listed service that the facade and the interface have the same members, that each facade member (and each static property getter) makes exactly one call on the instance with the same arguments and returns its result (`RecordingProxy` answers `true`, `4242`, `4.5f`, a fixed `DateTime` or the second value of an enum for value types, so a facade that returns a default fails), that the container holds one instance of the instance class, that the instance has no handlers, and that `ConvertedServices.json` lists exactly the services `ServiceRegistrations` registers (apart from `IDBService`). A facade member the test checks is a public or `internal` static method (native code calls an `internal` one, such as `ChatPortraitTells.RecordChatLine`) or a public static property getter.
- **Local variables**: the engine fake only records `SetLocalInt` and friends. `Tests/Support/LocalVariables` gives a `FakeNWScript` real local variables (what the code sets is what the matching `GetLocal...` answers until a `DeleteLocal...`); clear the fake's recorded calls through its `ClearCalls`. `Tests/Support/LoadedPlanets` builds a planet instance with its cache filled by the module handler, for tests of the area-to-planet rules.
- **Code that reaches a facade without a server**: a unit test of other code (a quest definition that names a guild, a migration that names a market category) calls the static facade, which needs a container. Give the fixture a `FacadeContainer` (`Tests/Support`): build it in `[OneTimeSetUp]` (call a cache handler such as `Guild.LoadData()` inside `using (container.Install())`), install it in `[SetUp]` and dispose that scope in `[TearDown]`. Without one the call throws `ContainerNotBuiltException`. This includes the tests of another converted service that calls the facade of this one (the `PlayerList` tests reach `HoloCom.GetCallState`), and a fixture of an instance that calls a facade of a service that converts later (the `HoloCom` and `Traps` fixtures install one for `DMPresence`). A test of the code that calls a facade, not of the service behind it (the trash can and the destroy item dialog call `ItemTrash.Audit`), replaces that registration: `new FacadeContainer(services => services.Replace(ServiceDescriptor.Singleton<IItemTrashService>(recorder)))`. Window definitions and view models that read the `KeyItem` cache (the Key Items window, `GuiLayoutValidationTests`, `DMToolWindowTests`) need the container too.
- **Roslyn harnesses that borrow a converted service**: a test of code that is not converted yet (the chat routing, the DM toolbar handlers) can compile the service's methods into its own stand-in static class, with `Method("Service/<Name>.cs", ...)`. Once the service is converted that method is a forwarder, so point the harness at the instance class: `InstanceMethod("Domain/<Domain>/<Name>Service.cs", ...)` and `InstanceField(...)` (`DMPossessionHarness`) return the member as a static one, and the stand-in declares static fields for what the instance injects (`_db`, `_presence`) with one-line shims to its own stand-ins. A test whose subject is the converted service itself becomes an ordinary instance test instead: `DMPossessionEngine` (`Tests/Support`) is the harness's model of DM possession behind the engine seams, and `FakeJsonEngine` gives a `FakeNWScript` working `Json` values and templates.
- **Coverage**: at least 70% of the service's lines (the facade, the interface and the instance class). Measure with the repository's settings, which exclude generated code:

  ```bash
  dotnet test SWLOR.Game.Server.Tests --no-build -c Release --collect "XPlat Code Coverage" --settings coverlet.runsettings --results-directory <dir>
  ```

  then read `line-rate` per class in the `coverage.cobertura.xml` it writes (or run all projects with `scripts/ci/run-unit-tests.sh --out <dir>`, which merges them). Report the number before the conversion and after it.
- **Behaviour must not change**: `SWLOR.Game.Server.CharacterizationTests` snapshots stay byte for byte; do not regenerate them.

## Rules the architecture tests enforce

`SWLOR.Architecture.Tests` (`ConvertedServicesTests`) reads the compiled server and fails with a message naming the type and member:

- **The pieces exist.** A listed service has the static class `Service.<Name>`, the interface `Domain.<Domain>.I<Name>Service` and a class `Domain.<Domain>.<Name>Service` that implements it, and the domain agrees with `DomainMap.json`.
- **No static state.** No type of a converted service (the facade, the interface, the instance class, the types in `Service/<Name>Service/`) holds mutable static state. `const` is allowed, and so is a `static readonly` field of a deeply immutable type (`ConvertedServiceRules.StaticMutableFields`): primitives, `string`, enums, `Regex`, `TimeSpan`, `DateTime` and `Guid`, `System.Collections.Frozen` and `System.Collections.Immutable` collections of such elements, `Nullable<T>` and value tuples of them, and sealed records and record structs whose members are all init-only and of such types. Arrays, `List`, `Dictionary`, `HashSet`, interface types such as `IReadOnlyList<T>`, a class with a settable member and any type the check cannot prove immutable are still reported. A constant table is a `static readonly` field of such a type, never a getter that builds a new value on each read (hot paths read these tables). Frozen collections do not keep insertion order, so a table that callers iterate is an `ImmutableArray` or `ImmutableList` (or an ordered key list beside the lookup), and a public `IReadOnlyList<T>` member returns a private `ImmutableList<T>` field, which allocates nothing per read. A table that needs the engine, a service or a facade is not built in a static initializer: it stays in an instance field built by the service.
- **Handlers stay on the facade.** A `[NWNEventHandler]` on any type of a converted service that is not one of its listed facades (the main one or a further facade) fails.
- **The instance never calls its own facade.** (A part has none.)
- **No service location.** Nothing outside `Composition/` uses `IServiceProvider` or any `Microsoft.Extensions.DependencyInjection` type, and nothing outside `Composition/` and the facades of converted services uses `FacadeAccessor`.
- **Domain types name their service.** A type in `Domain.<Domain>` is classified as the service of that domain whose name starts its name (`IAchievementService`, `AchievementService` and `AchievementNotification` are all the service `Achievement`), so the cross-domain baseline (`CrossDomainEdges.txt`) is the same before and after a conversion. A type that names no service of its domain shows up as a new `Platform/Domain.<Domain>` edge.

The composition root (`Composition/`) names every service it registers, so its outgoing edges are left out of the cross-domain guard (`wiringPlatformAreas` in `DomainMap.json`).

## Pitfalls

- **Name clash.** `Service.<Name>Service` is a namespace (the support types) and `<Name>Service` is also the instance class. Inside `namespace SWLOR.Game.Server.Service` the simple name means the namespace; the facade refers to the interface only.
- **No new support namespaces (owner decision, 2026-11-06).** Do not add a `Service.<Name>Service` namespace that does not exist yet: a new type goes in `Domain.<Domain>`, its name starting with the service's name. The existing ones move in P2-Z2. Until the `Combat` facade goes, `Domain.Combat` hides it from other `Domain.*` code: write `Service.Combat.X` there.
- **Runtime state in `Feature/` static classes.** The class stays where it is and keeps its `[NWNEventHandler]` methods and stateless logic, so handler names and the manifest do not change. Its runtime state (per-player dictionaries, cooldowns, schedules, caches) moves to an instance service: an existing service of that domain when one owns the subject, otherwise a new one with the usual pieces (`Service.<Name>` facade, `Domain.<Domain>.I<Name>Service`, `<Name>Service`, registration, `ConvertedServices.json`, `DomainMap.json`). The `Feature` class calls the facade. A table that nothing writes after it is built becomes a `static readonly` field of a deeply immutable type and stays in the class.
- **Package.** `Microsoft.Extensions.DependencyInjection` 9.0.9 is the version the toolset already uses (`SWLOR.Toolset.csproj`); `SWLOR.Game.Server/packages.lock.json` and the lock files of the toolset projects that reference the server record it. Change the version everywhere at once, then `dotnet restore <project> --force-evaluate` (add `-p:Configuration=Release` for the `packages.Release.lock.json` files) for the server and each toolset project.
- **Test projects see `Domain` as a namespace.** A test namespace `...Tests.Domain.<Domain>` is fine; spell the production types with a `using SWLOR.Game.Server.Domain.<Domain>;`.
- **Engine structures.** Production code that makes a real engine structure (`new Location(IntPtr.Zero)`) crashes a unit-test process when the garbage collector finalizes it, because the finalizer calls the native library. Fakes avoid this (`EngineStructures.Create`); for a structure the service makes itself, put the construction in a `protected virtual` method and override it in the test (`ChatCommandService.CreateEmptyLocation`).
- **Shared statics the instance reaches.** A converted instance still calls services that are not converted. Their static state is shared between tests: `Scheduler.Schedule` leaves an item that another test's `Scheduler.Process()` runs against whatever engine is installed then (drain it with `Scheduler.Process()` in `TearDown` while your fake is installed), and `Authorization.GetAuthorizationLevel` and `Disguise`/`PlayerName` lookups of a real player read the static `DB`. A test that must pass them uses an object the fake engine reports as a non-player, or `SWLOR_SUPER_ADMIN_CD_KEY` set for the test to the CD key the fake returns.
- **Engine tests that called private statics by reflection** (`typeof(Party).GetMethod("AddToParty", ...)`) reach the instance through `EngineTests/Framework/PartyCaches.cs`, which reads `CompositionRoot.ServerHost.Provider`. Tests outside the server assembly may do that; the architecture rule is about the server assembly.
- **Offline callers.** A pure method of a converted service (`PlayerMarket.GetBaseItemMarketCategory`, which an offline migration calls) still goes through the facade and so needs the container. The server's boot builds it before any handler; tests install a `FacadeContainer`. The module editor (`SWLOR.Toolset`) has no container at all: it must not call a facade member at run time. The one it used (`Item.IsEconomyRestricted(BaseItem, ...)`, the data-only economy classifier) moved into a stateless static helper beside the service (`Service/ItemService/EconomyRestriction.cs`, no fields, no handlers), which the instance calls and the editor calls directly. Before converting a service, search `SWLOR.Toolset*`, `SWLOR.CLI` and `SWLOR.CombatSim` for its members.
- **Private constants and tests that read them.** A test that reflected on a private member of the old static class (`Bank.StorageId`) follows it to the instance class; a test that read the old file's text (`LeadershipCivicPerkRegressionTests` reading `Guild.cs`) follows the code to `Domain/<Domain>/`.
- **Members the unit tests cannot reach.** A call into a not-yet-converted service that needs the native engine or the static database cannot run offline: `Gui.TogglePlayerWindow` (its window table), `Space.IsPlayerInSpaceMode` (`DB.Get`), the `NWNXLib` structures that `DMPresence.GetIsManifested` reads, and the player list `Area` fills in an event handler. The instance tests leave those lines to the in-engine tests, and the window logic around them stays covered by the harness tests of the code that shows the windows (the DM toolbar, the emotes window) through `InstanceMethod`.
- **Out parameters and engine structures on a facade.** `RecordingProxy` writes a default into an `out` value-type parameter (an `out bool` otherwise fails the proxy's write-back) and suppresses the finalizer of an engine structure it returns (`Json`, `Location`), which would crash a process with no engine.
- **A support type with handlers or static state in the service folder.** The architecture rules apply to every type that `UnitClassifier` puts in the service, and `Service/<Name>Service/*` is the service `<Name>` by namespace. A static class there that keeps `[NWNEventHandler]` methods or static fields (`Service/QuestService/QuestEncounter.cs`, a static class with five handlers and two static dictionaries) fails `Event_handlers_of_converted_services_stay_on_the_facade` and `Converted_services_hold_no_static_mutable_state` as soon as its service is listed, and its handler names are pinned by the manifest. Convert it as a further facade (section "A service of several classes") in the same pull request as its service. A small static helper with no state and no handlers is not a service: leave it static, or make it an instance the service owns.

- **One support folder for several services.** The eight DM services share `Service/DMToolService/` (the unit `DMTool` in `DomainMap.json`): its pure helpers (`DMSearchText`, `DMFavoriteList`, ...) are not services and stay static; the instance classes call them directly.
- **Data types and pure utilities next to a service.** A record or result type (`CasinoSpinResult`, `BankItemPage`) is not a service and stays where it is. A static class with no state and no engine, database or service calls (`CasinoSlotPresentation`: constants and pure functions over a payout; `CasinoPlayTracker`: pure functions over a `CasinoDailyPlay` and a time passed in) is a utility (decision of 2026-11-03, `MaintainabilityRefactorSpecs.md`): no interface, no registration, and the instance class of the service next to it calls it directly. They stay in `DomainMap.json` because they live in the `Service` namespace.
- **A facade that was not a static class.** `Area` was a non-static class with only static members; the facade must be a static class (`ConvertedServiceRules`), which no caller notices. A `Dictionary` the old class handed out by reference (`Area.GetAreas()`) is still the instance's own dictionary.
- **A nested public type or a static catalog in the old class.** `Music` was a class with a nested `Song`; the facade is a static class and the instance must not name it, so `Song` moved to `Service/MusicService/Song.cs` (nothing named `Music.Song`; callers only used `var`). `MusicSongCatalog.Songs` was a static auto-property, which the no-static-state rule counts (its backing field), so the catalog became a class that the service builds once (`new MusicSongCatalog().Songs`, kept in an instance field). Code outside the service asks the facade: `KeyItemIcon` calls `Music.TryGetCollectibleSong`, so `KeyItemIconTests` installs a `FacadeContainer`.
- **A support type with a static table.** `StructureChangedAction` (`Service/PropertyService/`) kept the structure-changed actions in a static dictionary that `BuildSpawnActions()` filled; the no-static-state rule counts it, so the dictionary is a local of `BuildSpawnActions()` and `PropertyCatalogService` builds it once into an instance field. Support types that call the service back (`Property.AssignPropertyId`) keep doing so through the facade.
- **Core services (`Authorization`, `Cache`, `Messaging`, `PlayerFeedback`).** `Cache` takes `IItemService` (the item service does not take `ICacheService`, so there is no cycle) and its private item name dictionary stays a private property of the instance: the fixtures that fill it without an engine (`AbandonedStationTests`, `HutlarDroidFoundryQuestTests`, ...) call `CacheItemNames.Seed(facades, names)` (`Tests/Support`). `Authorization` was a non-static class with one static method; the facade is a static class. `Messaging.BuildMessageDelegate` was nested in the old class; the instance cannot name its facade, so the delegate is `Service/MessagingService/BuildMessageDelegate.cs` (callers outside the service now write `BuildMessageDelegate` with `using SWLOR.Game.Server.Service.MessagingService;`). `PlayerFeedbackService` reads the settings, the clock and the display name through `protected virtual` methods (`GetSettings`, `UtcNowTicks`, `GetDisplayName`) so its tests control them (`Tests/Support/TestSettings` builds `ApplicationSettings` for a test). ## A service of several classes

Most services are three pieces (facade, interface, instance class). A service can be more than that, and lists the other classes under `"extras"` on its `ConvertedServices.json` entry. There are two kinds of extra, and one rule set for both:

```json
{ "name": "Quest", "domain": "Quests", "extras": [ { "facade": "QuestService.QuestEncounter" } ] }
{ "name": "Property", "domain": "World", "extras": [ { "part": "PropertyCatalog" }, { "part": "PropertyCityGovernance" }, { "part": "PropertyLoader" } ] }
```

- **A further facade** (`"facade"`, a type name relative to `SWLOR.Game.Server.Service`) is another static class in the service's namespace that keeps `[NWNEventHandler]` methods or static state. It stays a static class, so its handler names never change, and forwards to its own instance class.
- **A part** (`"part"`, a plain name) is a class a large service is split into by responsibility. It has no static class; the main facade forwards to it through the main interface.

Either kind is named after its type `<Type>`: the instance class is `<Type>Service` behind `I<Type>Service`, in the domain namespace of the service, registered in `ServiceRegistrations` and counted as a service of the container. The type name must start with the service name followed by a capital letter (`QuestEncounter`, `PropertyCatalog`) so the cross-domain guard counts the classes as the same unit and the baseline does not change; the list test says so when it does not, and when an extra shares its class with another or is the service's own. The list is sorted by name.

The rules apply to every class of the service: the pieces exist (a further facade is a static class; a part has none), no static state, handlers only on a listed facade (any of them), no use of its own facade, no service location. `FacadeForwardingTests` runs the forwarding checks for each facade as a case of its own (named by the facade, `QuestService.QuestEncounter`), and checks of the container (one singleton per class, no handlers on an instance class, the registered services are exactly the listed ones) for every class, parts included.

### Further facades

A further facade is converted exactly like a service of its own:

- The facade stays a static class in its own file with the same public members, constants and handlers, forwarding to `FacadeAccessor.Resolve<IQuestEncounterService>()`.
- The interface and the instance class sit in the domain namespace of the service (`Domain/Quests/IQuestEncounterService.cs`, `QuestEncounterService.cs`).
- Two instances of one service may need each other. They cannot both take the other by constructor; inject in one direction (`QuestService` takes `IQuestEncounterService`) and let the other call the static facade of the first (`QuestEncounterService` calls `Quest.GetQuestById`). The rule only forbids an instance calling its own facade.
- The list test fails with a message for an unknown facade type, a facade outside `Service.<Name>Service`, a duplicate or unsorted name, and a missing interface or instance class.

The pitfalls and test patterns are the same as for a service: the tests that read the facade's source read the instance class (`Domain/Quests/QuestService.cs`), and the engine tests reach the private members of an instance through the container (`EngineTests/Framework/QuestInternals`).

### Parts

A service of a few thousand lines is converted as several parts (`Property`: the definitions catalog, the instance loader, the city governance and the service itself). The facade and the public interface stay one: `Service.Property` and `IPropertyService` have exactly the old class's public members.

- **Ownership.** Static state moves to the part that owns it; a part that must clear another part's state for one key gets a small method for it (`PropertyLoaderService.ForgetProperty`, the verbatim lines `DeleteProperty` used to run). Members of a part that other parts call are public members of its interface; the rest stay private.
- **No cycles.** Parts depend on each other through constructor-injected interfaces, and the dependency graph must be a tree (`PropertyService` takes the catalog, the loader and the city governance; the loader and the governance take the catalog; the catalog takes `IAreaService`). Where two classes would need each other, one of them calls the other through a static facade, which resolves at call time (`StructureChangedAction`, a support type of `Property`, calls `Property` this way). A part has no facade of its own, so the rule against calling one's own facade covers only the main instance.
- **Forwarding.** `PropertyService` implements every member of `IPropertyService`: the ones it owns hold the logic, the others are one-line forwards to the part (`return _loader.GetPropertyLoadState(propertyId);`). Logic that calls a member another part owns calls the part's interface (`_catalog.GetLayoutByType`), or its own forward when it is public on the service.
- **Tests.** Test each part against its own fakes, and the service with the real parts over one scripted world (`Tests/Domain/World/PropertyWorld` builds the engine fake, a `QueryableDBService`, the area and planet stand-ins, the real catalog and the other parts, with the seams above replaced). A part's constructor is as free of work as a service's.
- **Combat (`CombatRecorder`, `Telegraph`).** The namespace `SWLOR.Game.Server.Domain.Combat` captures the simple name `Combat` in every file below `SWLOR.Game.Server.Domain` (and in test namespaces below `Tests.Domain`): the calls to the `Combat` facade in `BeastMasteryService`, `WeatherService` and `BeastMasteryServiceTests` are spelled `Service.Combat` (`SWLOR.Game.Server.Service.Combat` in the tests). `CombatRecorderService` takes `IDMPresenceService` and `IDBService`; its calls into `Ability`, `Stat`, `Combat`, `Scheduler`, `Log`, `TemporaryHitPointEffects`, `CombatRecorderEffectHooks` and `ApplicationSettings`, the server frame and the clock are one-line `protected virtual` methods, used only on the recording paths (a hook costs the `IsRecording` check while no recording runs). The only background thread is `CombatRecordWriter`'s: it owns its queue and files and calls only the static `Log`, never the recorder or the engine, so it needs no container. The scope structs dispose through the `CombatRecorder` facade, so a test of the instance installs a `FacadeContainer` that holds it (`CombatRecorderServiceTests`). `TelegraphService` takes `IDMPresenceService` and `IPartyService`; fixtures that run status effects (`StatusEffectBase.ApplyEffect` asks `CombatRecorder.IsRecording`) or the party instance need a `FacadeContainer` or a stand-in `ITelegraphService`.
- **Gathering sessions (`Slicing`, `Scavenge`, `Prospecting`).** Three units of the Crafting domain, each a main service plus one further facade named in `extras`. `Scavenge` and `Prospecting` own their engine world (`NwnScavengeWorld`, `NwnProspectingWorld`, which take `IDBService` instead of the static `DB`; `NwnScavengeWorld.Instance` and `NwnProspectingWorld.Instance` now return `Scavenge.World` and `Prospecting.World`, the way the craft worlds do), and `ScavengeSessions` and `ProspectingSessions` are facades of `ScavengeSessionsService` and `ProspectingSessionsService`, which hold the one lifecycle (the visits in progress) and keep the death and exit handlers on the facade. The lifecycle is built on first use through a `protected virtual` method, so a test hands it a fake world. `Slicing` has no engine world: its main service (`SlicingService`) is the register of attempts by player id (the old static dictionary), and `SlicingSession` is the facade of `SlicingSessionService`, which takes `IDBService`, `ISlicingService`, `IItemService`, `IGuiService`, `ISpawnService` and `ICacheService`; the unconverted `Perk`, `Stat`, `Skill`, the log and the clock are `protected virtual` one-liners. The session types that were nested in the facade (`ActiveSlicingSession`, `EligibleSlicingTool`, and `SlicingSessionSnapshot`, formerly `SessionSnapshot`) are files of `Service/SlicingService/`, because an instance may not name its facade. The pure board helper `SlicingService.Slicing` keeps its name and the new facade `Service.Slicing` shares it, so a file that imports both namespaces and means the helper adds `using Slicing = SWLOR.Game.Server.Service.SlicingService.Slicing;` (tests, `SlicingViewModel`). The static tables of the folder are `static readonly` fields of immutable types (the `SlicingReward` item lists as `FrozenDictionary` and `ImmutableArray`, the `SlicingRewardCatalog` entries as an `ImmutableArray` built once by a private `Builder`, with `SlicingRewardEntry` now a sealed record, and the generated `EncodedBoards` as a `FrozenDictionary<int, ImmutableArray<string>>`; the generator `tools/SWLOR.SlicingBoardGenerator` writes that field).
- **Performance helpers (`PerformanceSong`, `PerformanceSnapshot`, `PerformanceInspired`, `PerformanceRider`).** Four parts of `Performance` in `Domain/Social` replace the static `PerformanceSongs` (choice logic), `PerformerSnapshotBuilder`, `PerformanceInspiredApplier` and `PerformanceRiderCatalog.GetRequiredRank`. The song part takes `IMusicService`; the others put their `Perk`, `Stat`, `StatusEffect`, `AbilityEffectScaling` and `Performance` facade calls behind `protected virtual` methods. `PerformanceSongs` keeps only the `AutomaticSong` constant and `PerformanceRiderCatalog` its pure perk tables. The audience, windows and main services take the parts by constructor (their existing `BuildSnapshot`, `ChooseSong` and `ApplyInspired` seams now call them); the options window reaches the song list, the chosen song and the required rank through `Performance.GetAvailableSongs`, `ChooseSong` and `GetRequiredRank`. `Service/RoleplayXPService/` holds only pure statics and a file reader with no state, so it stays as it is.
